# Bank Statement Extraction Agent

Извлечение банковской выписки из PDF: реквизиты счёта, итоги за период и полный
список операций. Один вызов, один структурированный результат.

```python
from bankstatement.extract import extract

result = extract('samples/Great Lakes Commerce Bank 2025.pdf')
```

Отличие от обычного парсера в одном: **система не выдаёт результат, которому сама
не доверяет**. В каждой выписке напечатано `начало + приход − расход = конец`, и
это не украшение отчёта, а оракул — функция, проверяющая любой набор извлечённых
строк без разметки и без человека. Период объявляется верным только тогда, когда
арифметика документа сошлась до копейки; иначе он уходит с пометкой `failed`,
дельтой и диагнозом причины.

Для аудита это принципиально: молча выданная неверная цифра хуже пустой графы.

---

## Быстрый старт

```bash
uv sync
brew install tesseract        # macOS; нужен только для сканов
uv run poe extract "samples/Great Lakes Commerce Bank 2025.pdf"
```

Ещё команды:

```bash
uv run poe evaluate           # прогон по всем образцам с таблицей точности
uv run poe tests              # тесты
uv run poe check              # ruff + mypy strict
uv run poe hooks              # поставить pre-commit: те же проверки на коммите
```

В CI (GitHub Actions, Python 3.12 и 3.13) прогоняются ровно эти проверки плюс
порог покрытия. Tesseract там ставится намеренно: без него тесты на образцах
прочитали бы пустые страницы и упали, а это как раз то, что должно быть заметно.

Интерфейс — отдельной группой зависимостей, ядру он не нужен (в клоне он уже
стоит: группа `dev` тянет обе, иначе не проверить типы и не прогнать тесты):

```bash
uv sync --extra ui            # если ставить пакет, а не разрабатывать
uv run poe ui                 # http://127.0.0.1:8000
```

Так стенд работает в одном процессе и ничего не требует. Когда нужен отдельный
воркер — поднимается Redis, и та же команда переключает режим:

```bash
docker compose up -d redis
export BANKSTATEMENT_REDIS=redis://localhost:6379
uv run poe worker             # разбор уезжает сюда
uv run poe ui                 # API остаётся здесь
```

Разница только в том, где выполняется разбор и где лежит его состояние. Код выше
об этом не знает: `JobStore` и диспетчер выбираются один раз при старте.

Переменная нужна обоим процессам, и стенд после её установки надо перезапустить:
стенд без неё разбирает документы сам, а воркер рядом честно ждёт задач, которых
не будет. Какой режим выбран, показывает `GET /health` полем `mode` и первая
строка лога стенда.

Проверено на живом Redis: рестарт API посреди разбора 99-страничной подшивки
работу не теряет — воркер продолжает, а браузер после перезагрузки видит тот же
прогресс и уже готовые выписки. Счётчики метрик тоже переживают рестарт: они
лежат в общем хранилище, а не в памяти процесса.

Брокер — потоки Redis, а не список: у потока есть подтверждение после
выполнения, и документ, на котором воркер умер, не исчезает. Разбор идёт
минутами, так что случай не гипотетический.

С одной оговоркой, которая выяснилась замером, а не чтением документации:
перевыдачу `taskiq-redis` выполняет только после того, как прочитал новые
сообщения, поэтому на простаивающей очереди зависший документ ждёт следующей
задачи, а не срока. Стенд в это время не врёт: он показывает, что воркер молчит,
и продолжает следить.

CLI возвращает ненулевой код, если хотя бы один период не сведён: в конвейере это
должно останавливать выгрузку, а не проходить незамеченным.

### Образцы

Выписок в репозитории нет: это реальные документы. Чтобы повторить замер,
положите четыре PDF в `samples/` с теми же именами, что у файлов в
[`evaluation/truth`](evaluation/truth), иначе колонка «шапка» останется пустой,
и запустите `uv run poe evaluate`. Любую другую выписку можно проверить так же
(`uv run poe extract путь.pdf`) или загрузить через интерфейс `uv run poe ui`.
Тесты, которым нужны образцы, без них пропускаются; стенд и CLI проверяются на
синтетической выписке из `tests/conftest.py`, и порог покрытия держится и без
документов.

## Архитектура

Точка входа одна: `bankstatement.extract:extract(pdf_path) -> dict`; CLI и стенд —
тонкие обёртки над ней. Конвейер:

```
ingest → recognize → layout → segment → header → parse (гипотезы) → reconcile → report
```

- **recognize** — единственный шов между пикселями и логикой: любой движок отдаёт
  `Word(text, bbox, page, confidence, engine)`, и выше никто не знает, откуда взялись
  токены.
- **layout** — строки и денежные колонки по геометрии слов, а не по мнению движка.
- **segment** — один PDF может быть подшивкой: выписка начинается там, где объявлен
  её остаток на начало; реквизиты собираются голосованием страниц.
- **header** — итоги, счёт, банк, период. Подписи — открытый список синонимов, а
  между кандидатами выбирает инвариант шапки `beginning + deposits − withdrawals =
  ending`. Порядок день/месяц выводится из самих дат документа.
- **parse** — две гипотезы прочтения страницы (цепочка остатков и секции с
  заголовками); модуль между ними не выбирает.
- **reconcile** — оракул: единственное место, где период объявляется верным. Ничего
  не чинит, а при расхождении объясняет его форму: задвоение, не та колонка,
  перестановка цифр.
- **extract** — отдаёт гипотезы оракулу, а забракованный период переспрашивает на
  следующей ступени распознавания, только по спорным страницам и только пока он не
  сведён.

Каскад стоимости: цена зависит от трудности документа, а не от числа страниц.

| Ступень | Движок | Цена | Что закрывает |
|---|---|---|---|
| L0 | текстовый слой PDF | $0 | Great Lakes |
| L1 | Tesseract, 300 dpi ×2, `--psm 4` | $0 | Fulton, Renasant, Ixonia |
| L1b | Tesseract, 400 dpi, `--psm 6` | $0 | периоды, которые оракул забраковал |
| L2 | vision-модель, OpenAI или Anthropic | платно | страницы периодов, которые не свели бесплатные ступени |

Ступень L2 выключена по умолчанию и включается переменными окружения. Модель
получает картинку страницы и переписывает её построчно, дальше её текст проходит
тот же путь, что и текст Tesseract, и принимается только если период сошёлся
лучше. Бюджет страниц на документ ограничивает счёт:

```bash
export BANKSTATEMENT_VISION=openai             # или anthropic
export OPENAI_API_KEY=...                      # для anthropic — ANTHROPIC_API_KEY
export BANKSTATEMENT_VISION_PAGES=20           # страниц на документ, по умолчанию 40
export BANKSTATEMENT_VISION_MODEL=gpt-5.4-mini,gpt-5.6-sol  # необязательно; умолчания gpt-5.4-mini и claude-opus-5
uv run poe extract "samples/Binder 2.pdf"
```

Моделей может быть несколько, через запятую, и каждая — своя ступень лестницы:
эскалация отдаёт следующей только те выписки, которые предыдущая не свела.
Бюджет страниц — на каждую модель.

Те же переменные можно держать в `.env` рядом с `pyproject.toml`: poe читает его
сам. Значения из файла перекрывают переменные оболочки, так что бюджет, заданный
в `.env`, экспортом не переопределить.

Контракт клиента — один метод: картинка и подсказка на входе, текст на выходе
(`recognize/vision.py`, `VisionClient`). Реализации на официальных SDK лежат
рядом, тест подставляет заглушку без сети.

Замер на подшивке Ixonia, где бесплатные ступени сводят две выписки из десяти.
Эскалация отдала модели одни и те же сорок страниц восьми несведённых выписок;
расход — 2,6 тыс. токенов на входе и 1,5–1,9 тыс. на выходе за страницу, цены из
прайса OpenAI на 3 сентября 2026. Цена mini замерена по токенам прогона (105 тыс.
на входе, 61 тыс. на выходе), остальные оценены по расходу на страницу:

| Модель | Сведено | Время подшивки | Цена за 1M токенов, вход / выход | Цена подшивки |
|---|---|---|---|---|
| без L2 | 2 из 10 | 2 мин | — | $0 |
| gpt-5.4-mini, умолчание | 7 из 10 | 3 мин | $0.75 / $4.5 | $0.35 |
| gpt-5.6-terra | 5 из 10 | 5 мин | $2 / $12 | ≈ $1.1 |
| gpt-5.6-sol | 9 из 10 | 4,5 мин | $4 / $20 | ≈ $1.8 |
| mini, затем mini за несведённое | 9 из 10 | 4 мин | | $0.42 |
| mini, затем sol за несведённое | **10 из 10** | 4 мин | | $0.7–0.8 |

Две последние строки — две ступени внутри L2: вторая модель читала только
выписки, которые первая не свела. В двух прогонах sol понадобилась на восемь и
на одиннадцать страниц вместо сорока, и подшивка оба раза сошлась целиком за
меньше доллара. Цены этих строк замерены по токенам прогонов.

gpt-4o в таблице нет: на тех же страницах она ответила отказом на пять из
двадцати, среди них обычная таблица операций, а там, где читала, рвала цепочку
в двенадцати местах на странице. У моделей с рассуждением усилие задано низким:
переписать страницу — задача без рассуждений. Умолчание — самая дешёвая модель,
которая измеримо работает; за две оставшиеся выписки sol просит впятеро больше,
и это выбор пользователя, а не кода. Страница, которую модель прочесть не смогла
(отказ, пустой ответ, исчерпанный бюджет), остаётся в прежнем чтении: без этого
правила перечит проигрывал оракулу пустым местом, а не качеством чтения.

Два прогона mini дали по семь выписок, но разные семь: ответ модели от раза к
разу различается, и оракул принимает тот, что сошёлся. Поэтому второй проход той
же дешёвой модели по оставшимся выпискам — тоже ступень, и она даёт девять за
сорок два цента; одну выписку он оставил с невязкой в две копейки.

Ни одной ветки по имени банка и ни одной координаты в коде нет: правила общие, а
неверные прочтения отсеивает проверка. Каждое решение, вместе с тем, что пробовали
и отвергли, разобрано в [docs/INTERNALS.md](docs/INTERNALS.md).

## Интерфейс

Загрузить PDF (или открыть образец) → увидеть заключение, итоги, операции и — по
клику на номер страницы — **вырезку из исходного документа с рамкой вокруг той
самой строки**. Провенанс перестаёт быть полем в JSON: цифру видно на бумаге.

Отчёт устроен как аудиторский, от вывода к подробностям, а не наоборот:

1. **Заключение** — одно слово о документе целиком. Шкала взята из аудиторской
   практики, потому что она там уже есть: `подтверждено`, `подтверждено
   частично`, `не подтверждено`, `заключение невозможно`. Выводится механически
   из вердиктов оракула — своего мнения здесь нет.
2. **Объём проверки** — сколько выписок, страниц и операций стоит за этим словом.
3. **Что требует человека** — таблица расхождений **по убыванию суммы**, каждое
   со своей причиной и ссылкой на карточку. Расхождение в копейку и расхождение
   в двенадцать тысяч — разная работа, и порядок должен это показывать.
4. **Детали** — карточки выписок, операции, провенанс.

Без первых трёх пунктов итог приходилось собирать глазами по десяти карточкам:
что-то сошлось, что-то нет, а какой ответ — неясно. То же заключение печатает
CLI и отдаёт `meta.opinion` в JSON: три интерфейса рассказывают одну историю.

Приложение собирается фабрикой: `create_app(settings, container)`. Ничего не
создаётся при импорте — состав описан провайдерами **dishka**, настройки читаются
из окружения один раз. Отсюда два свойства, которых иначе не бывает: два
приложения с разными настройками живут в одном процессе, а тест подменяет
зависимость своим контейнером, а не атрибутом модуля.

Стек выбран по тому же признаку, что и всё остальное — минимум лишнего:
**FastAPI** отдаёт фрагменты HTML, **htmx** их подставляет, стили свои. Ни
сборки, ни node_modules, ни внешних CDN: htmx лежит в репозитории (50 КБ), и
страница работает офлайн. Он же и HTTP-API: `POST /jobs`,
`GET /api/jobs/{id}`, схема на `/api`.

Долгие файлы обрабатываются в фоне, а **разобранные выписки показываются по
мере готовности**: в подшивке из десяти первая сведена к пятнадцатой секунде, и
с ней уже можно работать, пока читаются остальные. Прогресс показывает и готовые
страницы, и те, что читаются прямо сейчас — параллельное чтение финиширует
пачками, и без второго числа полминуты работы выглядели бы простоем.

Что здесь есть от продового сервиса:

| | |
|---|---|
| **Кэш по содержимому** | тот же файл под другим именем возвращает готовый разбор мгновенно: SHA-256 вместо повторных минут OCR |
| **Пачка документов** | выписки приходят папкой за квартал; форма принимает до 20 файлов разом |
| **Очередь вместо отказа** | одновременных разборов не больше двух: каждый и так занимает все ядра, а память тратит кратно |
| **Ограничение частоты** | ведро с токенами на клиента — от случайного цикла в скрипте; на проде это место занимает шлюз |
| **`/health` и `/metrics`** | счётчики в формате Prometheus, включая главный — долю сведённых периодов |
| **Проверка входа** | не-PDF, пустой и слишком большой отвергаются до создания задачи |

Файл проверяется на входе. Не-PDF, пустой или слишком большой отвергается сразу и
с внятным текстом — а не падает через две секунды внутренней ошибкой библиотеки.
Коды при этом честные (`415`, `400`, `413`): то же API читают не только браузеры.
Путей на сервере в сообщениях нет, полный след уходит в лог.

## Что получается на выходе

Плоские `account` / `summary` / `transactions` повторяют первый период — контракт
задания выполняется буквально. Рядом лежит `periods[]` на случай подшивки из
нескольких выписок и `meta`: заключение по документу, объём проверки и то, чем и
как это прочитано. `meta.opinion` — тот же итог, что видит человек, только для
конвейера: по нему решают, уходит документ дальше или на стол аудитору.

```jsonc
{
  "account":  { "bank": "Great Lakes Commerce Bank", "account_last4": "4071",
                "period": { "start": "2025-01-01", "end": "2025-01-28" } },
  "summary":  { "beginning_balance": 2014882.47, "deposits_total": 2180764.90,
                "withdrawals_total": 2154309.25, "ending_balance": 2041338.12,
                "deposits_count": 134, "withdrawals_count": 158,
                "sources": {
                  "beginning_balance": { "page": 1, "bbox": [229.6, 111.4, 293.5, 125.1],
                                         "engine": "textlayer", "confidence": 100.0,
                                         "repaired": false, "printed": null },
                  "deposits_count":    { "page": 1, "bbox": null, "engine": "computed",
                                         "confidence": null, "repaired": false, "printed": null },
                  "//": "и так по каждому из четырёх итогов" } },
  "transactions": [
    { "date": "2025-01-01", "description": "CIGNA CLAIMS PAYMENT",
      "deposit": 8164.30, "withdrawal": null, "balance": 2023046.77,
      "source": { "page": 1, "bbox": [31.2, 204.6, 564.1, 216.3],
                  "engine": "textlayer", "confidence": 100.0,
                  "repaired": false, "printed": null } }
  ],
  "periods": [
    { "...": "то же плюс reconciliation и список страниц",
      "losses": { "placed": 292, "repaired": 0, "proven": true, "unplaced": [] } }
  ],
  "meta": { "source_file": "samples/Great Lakes Commerce Bank 2025.pdf",
            "opinion": "clean", "periods_total": 1, "periods_reconciled": 1,
            "unexplained": 0.0, "engine_stats": { "textlayer": 6 } }
}
```

Каждое значение несёт происхождение: страница, координаты, движок, уверенность.
Включая цифры в шапке (итоги, остатки, даты периода) — у каждого источник, где его найти в
исходном документе. Цифру можно показать пальцем на странице.

Счётчики операций печатает один банк из четырёх. Там, где их нет, доказанный период
получает их из той же арифметики, что подтвердила состав операций, и провенанс это
не скрывает: `engine: computed` вместо страницы с координатами. У недоказанного
периода счётчики остаются пустыми.

Два поля провенанса отвечают на вопрос, который в аудите задают первым. `repaired`
говорит, что число выбрано кодом, а не прочитано: OCR потерял разрядную запятую
или спутал символ, и разбор подобрал прочтение, которое сошлось с арифметикой.
`printed` показывает перекрытое чтение — `2,2/72,320.90` там, где в отчёт ушло
`2272320.90`. Без этой пары выправленная цифра неотличима от прочитанной, и
перепроверять её никто не станет.

`periods[].losses` — то, что разбор увидел, но не разместил: `placed` размещено,
`repaired` исправлено, `unplaced` перечислено поимённо, с провенансом и причиной.
Период с потерянными строками не получает заключение `clean`, даже если его
арифметика сошлась. Исключение названо явно: `proven` означает, что состав
операций доказан. Для класса A это цепочка, подтвердившая каждую строку: ещё
одной операции в ней не нашлось бы места, и строка в `unplaced` — повтор сводки
или служебный маркер, а не потеря. Класс B подтверждает суммы, но не состав, и
доказанным считается лишь тогда, когда каждая неразмещённая строка объяснена
маркером или дублем; необъяснённая строка оставляет период недоказанным, и
заключение о ней предупреждает.

## Класс гарантии

Разные выписки допускают разную строгость проверки, и смешивать их в одно
«извлечено успешно» нельзя.

| Класс | Что подтверждено | Когда |
|---|---|---|
| **A** | каждая операция по отдельности | есть колонка остатка: `balance[i] − balance[i−1] = amount[i]` |
| **B** | итоги за период, но не состав | колонки остатка нет |
| **C** | ничего | расхождение; период уходит на ручную проверку |

## Измеренная точность

Три критерия задания измеряются по-разному, и таблица показывает все три.

- **Шапка, точное совпадение.** Колонка «шапка»: сколько полей совпало с
  эталоном из [`evaluation/truth`](evaluation/truth) — периода, банка, номера
  счёта, четырёх итогов и двух счётчиков там, где банк их печатает. Эталон
  размечен руками по изображению первой страницы каждой из тринадцати выписок,
  а не снят с выхода программы.
- **Операции.** Колонка «сведено»: сколько периодов документ подтвердил
  собственной арифметикой, с классом гарантии A/B. Эталонного списка операций
  нет, и сверка идёт с итогами, напечатанными в документе; «потерь» — строки с
  датой и суммой, которые разбор увидел, но не разместил.
- **Обобщение.** Раздел «Чужие выписки» ниже: документы, которых не было при
  разработке.

Таблица получена прогоном `uv run poe evaluate` без платной ступени и не
правится руками; машинная версия — в
[`evaluation/latest.json`](evaluation/latest.json). Тот же прогон с двумя

Столбец «потерь» — строки с датой и суммой, которые разбор увидел, но не смог
пристроить: у секции нет применимого заголовка, сумма стоит вне колонки, число
не читается. Они не исчезают, а уходят в результат отдельным списком с
провенансом и причиной, и период с такими строками не может получить заключение
`clean`. Ноль здесь значит «разбор ничего не выронил», а не «разбор ничего не
заметил».

Столбец «стык» — независимая от разбора проверка: у выписок, примыкающих по
времени, конец одного периода обязан совпасть с началом следующего по тому же
счёту. Она ловит то, чего оракул одного периода увидеть не может: потерянную
выписку и неверную границу между ними.

## Известные слабости

Самый трудный образец: подшивка Ixonia сведена на две выписки из десяти. Разрывы
цепочки там на сотни тысяч — неверно прочитанные разряды в крупных переводах, то
есть предел Tesseract на скане низкого качества, а не логики разбора. Ступень L2
эти разрывы закрывает: семь выписок из десяти с моделью по умолчанию, девять с
сильной (таблица в «Архитектуре»). Таблица выше — бесплатный прогон: `poe evaluate`
идёт без ключа.

- **Vision-ступень измерена на одном документе.** Семь и девять из десяти —
  цифры с одной подшивки, не статистика; на другом скане модель может читать
  иначе. Координаты слов от модели синтетические: рамка провенанса показывает
  полосу страницы, а не точное место.
- **Номер счёта на редактированном скане.** Плашка, прижатая к цифрам, съедает
  первую: OCR читает «Account Number a 664», и поле остаётся пустым.
- **Имя банка** ищется по слову Bank или Credit Union; логотип, прочитанный как
  `bslxonia`, честно даёт пусто. По документу имя согласуется большинством выписок,
  и одна подшивка с двумя разными банками получит имя того, которого больше.
- **Два счёта в одном сегменте.** Если у второго счёта нет своей шапки с остатком
  на начало, его страницы приклеиваются к предыдущей выписке, а номер счёта
  решается большинством. Арифметика такого периода не сойдётся, и он уйдёт в
  `failed`, но причиной будет назван разрыв цепочки, а не второй счёт.
- **Ремонт суммы** по подмене символа принимается без подтверждения соседней
  строкой; со сдвигом разряда — только с ним. Провенанс любую правку показывает.
- **Макет без колонки остатка и без заголовков блоков** даёт в лучшем случае
  класс B, а без итогов в шапке — `failed`. Кредитные карты (обратный знак) и
  мультивалютные выписки не поддерживаются.
- **Чужие форматы.** Порядок день/месяц, знаки `£ € ₹`, даты вида `01 Jan 2024`
  читаются. Индийская разрядная сетка (`1,23,456.00`) читается как число, но при
  ошибке OCR не чинится; водяной знак поперёк страницы попадает в строки и в имя
  банка; описание, перенесённое на строку с суммой, эту сумму теряет.
